## WEEK 1 — Foundations: Linux + Networking + Docker (Days 1–7)
> **Why start here, not AWS:** AWS is just Linux machines connected over a network, packaged in a UI. If you don't understand Linux and networking, you will memorize AWS without understanding it. Interviewers catch that immediately. Build the base first — everything else becomes logical, not memory work.

### Day 1 — Linux Command Line Basics

**Interview Questions to Prepare:**

### Day 8 — VPC + Networking on AWS
**Morning Theory (6 hrs)**
- VPC (Virtual Private Cloud): your private network inside AWS
- CIDR blocks: how `10.0.0.0/16` gives you 65,536 IPs for your VPC
- Subnets: public subnet (internet-accessible) vs private subnet (internal only)
- Internet Gateway (IGW): the door between your VPC and the internet
- NAT Gateway: lets private subnet instances download updates without being exposed to internet
- Route Tables: defines where traffic goes — like a routing table on a router
- Security Groups: firewall at instance level — stateful (allows return traffic automatically)
- NACLs: firewall at subnet level — stateless (must allow both inbound and outbound explicitly)
- Watch: **"AWS VPC Explained" — Be A Better Dev (YouTube)**

**Evening Practical (5 hrs)**
- Create a custom VPC: `10.0.0.0/16`
- Create 2 public subnets (`10.0.1.0/24`, `10.0.2.0/24`) in different AZs
- Create 2 private subnets (`10.0.3.0/24`, `10.0.4.0/24`) in different AZs
- Attach an Internet Gateway to the VPC
- Create a public Route Table: add route `0.0.0.0/0 → IGW`, associate with public subnets
- Create a Security Group: allow inbound port 8080 (your app) and port 22 (SSH)
- Draw the VPC architecture on paper — label every component

**Interview Questions to Prepare:**
- What is the difference between Security Group and NACL?
- Why does a private subnet need a NAT Gateway (not IGW)?
- What happens if a Route Table has no route for `0.0.0.0/0`?

### Day 9 — EC2: Virtual Machines on AWS
**Morning Theory (6 hrs)**
- EC2 (Elastic Compute Cloud): Linux/Windows machines in the cloud
- Instance types: `t3.micro` (free tier), naming convention (t=family, 3=generation, micro=size)
- AMIs (Amazon Machine Images): pre-built OS templates — Amazon Linux 2023, Ubuntu 22.04
- Key Pairs: SSH access — you create key pair, AWS stores public key, you keep private key
- User Data: script that runs on first boot (install Java, pull code, start app — all automated)
- Elastic IP: static public IP that persists even if you stop/start the instance
- Purchasing options: On-Demand (pay per hour), Reserved (1-3 year commitment = cheaper), Spot (cheapest, can be terminated anytime)
- Watch: **"EC2 for Beginners" — Stephane Maarek (YouTube or Udemy)**

**Evening Practical (5 hrs)**
- Launch an EC2 instance (Amazon Linux 2023, t2.micro = free tier) inside your VPC (public subnet)
- Use your key pair from Day 2 (SSH key you already generated)
- SSH into it: `ssh -i your-key.pem ec2-user@<public-ip>`
- Once inside, you are on a Linux machine in the cloud — run `uname -a`, `df -h`, `free -m`
- Install Java: `sudo yum install java-21-amazon-corretto -y`
- Copy your Spring Boot JAR using `scp`: `scp -i your-key.pem app.jar ec2-user@<ip>:~/`
- Run: `java -jar app.jar &` → test from your laptop: `curl http://<ec2-public-ip>:8080/health`
- **Stop the instance when done** (Actions → Stop — not Terminate) to save free tier hours

**Interview Questions to Prepare:**

### Day 10 — S3 + Route53 + IAM Roles in Depth
**Morning Theory (6 hrs)**
- S3 (Simple Storage Service): object storage — not a file system, not a database
- Buckets and Objects: bucket is a container, object is a file + metadata
- Storage classes: Standard (frequent access), Standard-IA (infrequent access), Glacier (archival)
- Versioning: keep all versions of an object — recover from accidental delete
- Bucket Policies vs IAM Policies — both control access, how they interact
- Pre-signed URLs: give temporary access to a private object without credentials
- IAM Roles for EC2: instead of storing credentials on EC2, attach a Role — EC2 gets temporary credentials automatically — **NEVER hardcode AWS credentials in code (OWASP rule)**
- **Route53 (DNS service):**
  - Hosted Zone: collection of DNS records for a domain
  - Record types: A (domain → IPv4), CNAME (domain → domain), Alias (AWS-specific — points to ALB/CloudFront)
  - How DNS resolution works end-to-end when a user types a URL
  - Routing policies: Simple, Weighted (A/B split), Latency-based, Failover
- Watch: **"S3 Deep Dive" — AWS Official YouTube** + **"Route53 explained" — Be A Better Dev (YouTube)**

**Evening Practical (5 hrs)**
- Create an S3 bucket (globally unique name)
- Upload a file manually → try to access it from browser → see `Access Denied` (private by default)
- Enable versioning → upload same file again → see two versions
- Create a lifecycle rule: move to Standard-IA after 30 days
- Write a Spring Boot controller that uploads a file to S3 using AWS SDK v2:
  ```java
  S3Client s3 = S3Client.create();
  s3.putObject(PutObjectRequest.builder().bucket("your-bucket").key("file.txt").build(), path);
  ```
- **Use IAM Role attached to EC2 — do not hardcode access keys**
- Generate a pre-signed URL in code → test in browser (should work without AWS credentials)

**Interview Questions to Prepare:**
- What is the difference between S3 and EBS?
- Why should you never hardcode AWS credentials in your Spring Boot app?
- What is a pre-signed URL and when would you use it?
- What is the difference between CNAME and Alias record in Route53?

### Day 11 — RDS + ECS Fargate + ElastiCache
**Morning Theory (6 hrs)**
- **RDS (Relational Database Service):** managed MySQL/PostgreSQL/Aurora
  - Multi-AZ deployment: primary in AZ-1, standby in AZ-2 — automatic failover on failure → High Availability
  - Read Replicas: separate read-only copies → scale reads, not for failover
  - Key difference to remember: **Multi-AZ = HA (failover), Read Replica = Performance (scale reads)**
  - Aurora: AWS's MySQL-compatible DB — 5x faster, auto-scaling storage, serverless option
- **ECS Fargate (Elastic Container Service):** run Docker containers on AWS without managing EC2
  - Fargate vs EC2 launch type: Fargate = serverless containers (AWS manages the host), EC2 = you manage the host VMs
  - ECS concepts: Cluster, Task Definition (like Dockerfile but for ECS), Task (running container), Service (keeps N tasks running)
  - ECR (Elastic Container Registry): AWS's private Docker registry — like Docker Hub but in your AWS account
  - ECS vs EKS: ECS is simpler (AWS-managed orchestration), EKS is Kubernetes (more control, more complex)
- **ElastiCache:** managed Redis or Memcached on AWS
  - Redis use cases on your resume: session store, caching API responses, rate limiting, pub/sub
- Watch: **"ECS Fargate Tutorial" — Be A Better Dev (YouTube)** + **"RDS vs Aurora" — AWS re:Invent (YouTube)**

**Evening Practical (5 hrs)**
- Create an RDS MySQL instance (db.t3.micro = free tier) — **private subnet only, no public access**
- Create a Security Group for RDS: allow inbound 3306 **only from your EC2's Security Group** — not `0.0.0.0/0`
- SSH into your EC2, install MySQL client: `sudo yum install mysql -y`
- Connect from EC2: `mysql -h <rds-endpoint> -u admin -p` → create a table → insert data → query
- **ECS Fargate lab:**
  - Push your Docker image to ECR: `docker tag myapp:v1 <account>.dkr.ecr.ap-south-1.amazonaws.com/myapp:v1`
  - `aws ecr get-login-password | docker login --username AWS --password-stdin <ecr-url>`
  - `docker push <ecr-url>/myapp:v1`
  - Create an ECS Cluster (Fargate mode) → Task Definition (use your ECR image) → Service (1 task running)
  - Access via the public IP assigned to the Fargate task

**Interview Questions to Prepare:**
- What is the difference between Multi-AZ and Read Replica?
- What is the difference between ECS and EKS?
- What is the difference between ECS Fargate and ECS with EC2 launch type?
- Why should RDS be in a private subnet?

### Day 12 — Load Balancer + Auto Scaling + CloudWatch
**Morning Theory (6 hrs)**
- Elastic Load Balancer (ELB): distributes traffic across multiple EC2 instances
- ALB (Application Load Balancer): Layer 7 — routes based on URL path, hostname, headers — use for HTTP/HTTPS apps
- NLB (Network Load Balancer): Layer 4 — routes based on IP/port — use for ultra-low latency, TCP/UDP
- Target Groups: logical group of EC2 instances that receive traffic
- Auto Scaling Group (ASG): automatically add/remove EC2 instances based on load
- Scaling policies: Target Tracking (e.g. keep CPU at 50%), Step Scaling, Scheduled Scaling
- CloudWatch: AWS's built-in monitoring — metrics, logs, alarms, dashboards
- CloudWatch Alarm: trigger SNS notification or Auto Scaling action when metric crosses threshold
- Watch: **"ALB vs NLB" — AWS YouTube** + **"Auto Scaling explained" — AWS YouTube**

**Evening Practical (5 hrs)**
- Create an ALB in your VPC (public subnet)
- Create a Target Group → register your EC2 instance
- Create an ALB Listener rule: port 80 → forward to Target Group
- Access your Spring Boot app through the ALB DNS name (not EC2 IP)
- Create a CloudWatch Alarm: EC2 CPU Utilization > 70% → send email via SNS
- Create an SNS Topic → subscribe your email → confirm subscription
- Trigger the alarm by stressing the CPU: `stress --cpu 1 --timeout 60` (install with `yum install stress`)
- Check your email — alarm notification should arrive

**Interview Questions to Prepare:**
- What is the difference between ALB and NLB? When do you choose each?
- How does Auto Scaling know when to scale out?
- What is a CloudWatch Alarm and what can it trigger?

### Day 13 — Lambda + SQS + SNS (Event-Driven AWS)
**Morning Theory (6 hrs)**
- Serverless concept: you write code, AWS manages servers, you pay only per execution
- Lambda: runs code in response to an event — max 15 min execution, stateless
- Lambda triggers: S3 upload, API Gateway request, SQS message, scheduled (cron)
- Cold start: first invocation is slower because AWS spins up a container — subsequent calls are fast
- SQS (Simple Queue Service): message queue — decouples services, handles traffic spikes
- Standard Queue: at-least-once delivery, not ordered
- FIFO Queue: exactly-once, strictly ordered — use for financial transactions, order processing
- Dead Letter Queue (DLQ): messages that fail after retries go here — prevents message loss
- SNS (Simple Notification Service): pub/sub — one message, many subscribers (email, SQS, Lambda, HTTP)
- Fan-out pattern: SNS topic → multiple SQS queues (different services each process independently)
- **Kafka vs SQS — the comparison question you will get asked** ("your resume says event-driven, why SQS and not Kafka?"):
  - **Kafka**: messages are persisted on disk with a configurable retention period, consumers pull at their own pace using an offset (so you can replay old messages from any point). Ideal for high-throughput event streaming, audit trails, data pipelines to a data lake.
  - **SQS**: message is deleted once the consumer reads and acknowledges it (no replay). Fully managed by AWS with zero infrastructure overhead. Ideal for task queues, decoupling microservices, and simpler use cases.
  - Kafka-specific terms: **partition** (unit of parallelism), **offset** (position of a consumer in a partition), **consumer group** (multiple consumers sharing the work), **topic retention** (how long messages are kept).
  - SQS-specific terms: **visibility timeout** (message hidden while being processed), **DLQ** (dead-letter queue for failed messages), **at-least-once delivery**.
  - Your Mondee answer: "We chose SQS because our booking notification events don't need replay or long-term retention, and SQS's fully managed scaling fit our AWS-native stack. We would evaluate Kafka if we needed event sourcing, a consumer-group fan-out model, or a pipeline into a data warehouse."

### Day 20 — Redis Deep Dive (Caching + Pub/Sub + Distributed Locking)
**Morning Theory (6 hrs)**
- **Why Redis is everywhere on your resume** (Mondee + TCS both): Redis is the most versatile in-memory data structure store — used for caching, sessions, rate limiting, pub/sub, leaderboards
- **Caching patterns** (interview favorites):
  - **Cache-aside** (lazy loading): app checks cache first → if miss, fetch from DB → store in cache → return. Most common pattern.
  - **Write-through**: every write goes to cache AND DB simultaneously. Cache always has fresh data. Higher write latency.
  - **Write-behind** (write-back): write to cache first → async flush to DB. Fast writes, risk of data loss.
  - Cache invalidation: time-based TTL (expires automatically) vs event-based (explicit delete on update)
- **Redis data structures** (know at least these 3):
  - String: simplest — `SET key value EX 3600` (expires in 1 hour)
  - Hash: like a Java HashMap — `HSET user:1 name "Kanagarajan" email "k@example.com"`
  - List: ordered list — `LPUSH queue task1` (left push) — use for task queues
- **Redis Pub/Sub**: publisher sends to a channel, all subscribers receive. No message persistence. Use for real-time notifications.
- **Distributed Locking with SETNX**: `SET lock:payment:123 "locked" NX EX 30` — only one instance can set this (NX = only if Not eXists). Used to prevent duplicate payment processing.
- **Spring Boot integration**:
  - `@Cacheable` on a method — first call queries DB, subsequent calls return from Redis
  - `@CacheEvict` — remove from cache when data changes
  - `@CachePut` — always update cache after method runs

  - `thenApply()` → transform result, `thenCombine()` → merge two async results
  - `exceptionally()` → fallback on exception
  - Real use: call flight API + hotel API in parallel → combine → return combined result

- **Maven** (build tool — on your resume, interviewers ask this):
  - Maven lifecycle phases in order: `validate` → `compile` → `test` → `package` → `verify` → `install` → `deploy`
  - `mvn package` = compile + test + create JAR. `mvn install` = package + put in local `.m2` repo
  - POM.xml: `<dependencies>`, `<build><plugins>`, `<properties>` for version management
  - `<scope>test</scope>` = only available during testing, not in final JAR
  - `mvn dependency:tree` — see all transitive dependencies (useful for debugging version conflicts)
  - Interview answer: "We use Maven to manage dependencies, run tests in CI, and package the Spring Boot fat JAR for Docker deployment."
- **Design Patterns** (interviewers ask: "which pattern did Spring Boot use for X?" and "which pattern did you use in your service?"):
  - **Singleton**: one instance for the app's lifetime. Every Spring `@Service`, `@Repository`, `@Component` is Singleton-scoped by default.
  - **Factory**: `ApplicationContext.getBean()` — Spring is a bean factory. `BeanFactory` is the literal Spring interface. `@Bean` methods are factory methods.
  - **Builder**: `ResponseEntity.ok().body(data)`, `UriComponentsBuilder.fromPath(...)`, Lombok's `@Builder` — construct complex objects step by step without telescoping constructors.
  - **Strategy**: `PaymentStrategy` interface with `CreditCardStrategy`, `UPIStrategy` — swap behaviour at runtime without changing the caller. Your Mondee payment service.
  - **Observer**: Spring's `ApplicationEventPublisher` + `@EventListener` — publisher fires an event, all listeners react independently. Your Mondee event-driven flows.
  - **Proxy (AOP)**: `@Transactional`, `@Cacheable`, `@PreAuthorize` — Spring wraps your bean in a proxy and adds cross-cutting behaviour without touching your method.
  - Interview answer: "Spring Boot uses Singleton (beans), Factory (ApplicationContext), and Proxy (AOP) at its core. I used Strategy in Mondee's payment module to switch providers at runtime, and Observer via Spring Events for asynchronous downstream notifications."
- **Java Concurrency** (every senior backend interview goes here):
  - `synchronized` keyword: acquires the object's intrinsic lock — only one thread enters the block at a time. Simple but coarse-grained (locks the whole object).
  - `ReentrantLock`: `lock.tryLock(500, MILLISECONDS)` won't block forever. `lockInterruptibly()` can be cancelled mid-wait. Supports fair mode (threads acquire in arrival order).
  - `volatile`: guarantees every thread reads the value from main memory (not CPU cache). Fixes **visibility** but does NOT fix **atomicity** — use `AtomicInteger` for `i++` style operations.
  - Race condition: two threads read-modify-write the same variable without synchronization → wrong result. Example: two threads both read `counter = 5`, both add 1, both write `6` — final value should be `7`.
  - Deadlock: Thread A holds Lock 1 and waits for Lock 2. Thread B holds Lock 2 and waits for Lock 1. Both wait forever. Prevention: always acquire locks in the same fixed order across all code paths.
  - `ExecutorService`: `Executors.newFixedThreadPool(10)` — reuse threads instead of creating `new Thread()` each time. `submit()` returns a `Future`. Always call `shutdown()` when done.
  - **Java 21 Virtual Threads (Project Loom)**: JVM-managed lightweight threads — you can create millions without OS overhead. `Thread.ofVirtual().start(task)`. Ideal for I/O-bound work (HTTP calls, DB queries) where threads would otherwise block. Not beneficial for CPU-bound tasks.
  - Interview answer: "In Mondee's gateway we used `CompletableFuture` with a fixed thread pool for parallel upstream calls. After evaluating Java 21 virtual threads, we found them ideal for the RAG pipeline's I/O-heavy embedding and retrieval steps."

### Day 23 — Spring Boot Advanced (JPA + WebSockets + Microservices Patterns)
**Morning Theory (6 hrs)**
- **Spring Bean lifecycle**: Constructor → `@PostConstruct` → business logic → `@PreDestroy`
- **`@Transactional`**: wraps method in a DB transaction — if exception thrown → rollback all changes
  - Default: rollback on `RuntimeException` only — checked exceptions do NOT trigger rollback unless configured
  - Propagation: `REQUIRED` (join existing or create new), `REQUIRES_NEW` (always new transaction)
  - Isolation: `READ_COMMITTED` default — prevents dirty reads
- **JWT + Spring Security** (your Mondee resume bullet — every 24 LPA backend interview tests this):
  - JWT structure: `header.payload.signature` — all Base64-URL encoded. Header = algorithm (`HS256`). Payload = claims (`userId`, `roles`, `exp`). Signature = `HMAC(header + "." + payload, secretKey)` — proves the token was not tampered with.
  - Stateless auth: server stores nothing. On every request → extract `Authorization: Bearer <token>` header → verify signature → check `exp` (expiry) → extract claims → set `SecurityContextHolder`. No DB lookup.
  - Spring Security filter chain: write `JwtAuthenticationFilter extends OncePerRequestFilter`. It intercepts every request before it reaches your controller, validates the token, and populates `SecurityContextHolder` with the user's roles.
  - `@PreAuthorize("hasRole('ADMIN')")` — method-level authorization. Spring reads the `Authentication` from `SecurityContextHolder` and checks the role.
  - JWT vs OAuth2: OAuth2 is an **authorization framework** (it defines flows: authorization code, client credentials, implicit). JWT is a **token format**. In practice, the access token in an OAuth2 flow is usually a JWT.
  - Your Mondee answer: "Our Spring Cloud Gateway validates the JWT in a pre-filter before routing to any downstream service. The signing key is HS256, stored in AWS Secrets Manager, never hardcoded."
- **ACID Properties** (asked in virtually every database round):
  - **Atomicity**: all steps of a transaction succeed together or all are rolled back. No half-written state.
  - **Consistency**: the DB moves from one valid state to another. Constraints, foreign keys, and business rules are never violated by a committed transaction.
  - **Isolation**: concurrent transactions do not see each other's uncommitted writes (degree depends on isolation level).
  - **Durability**: once committed, data survives crashes. Achieved via Write-Ahead Log (WAL) — changes written to log on disk before data pages are updated.
  - Isolation levels in MySQL: `READ_UNCOMMITTED` (dirty reads OK) → `READ_COMMITTED` (Spring default — no dirty reads) → `REPEATABLE_READ` (MySQL default — same row read twice gives same result) → `SERIALIZABLE` (total isolation, lowest concurrency).
- **Spring Data JPA & N+1 problem** — this kills production performance:
  - You have 100 `Order` entities each with an `@ManyToOne User` — fetching all orders fires 1 + 100 DB queries
  - Fix 1: `JOIN FETCH` in JPQL query
  - Fix 2: `@EntityGraph(attributePaths = "user")` on the repository method
  - Fix 3: `@BatchSize(size = 20)` on the lazy collection
- **WebSockets** (your Mondee resume mentions real-time flight updates):
  - HTTP is request-response (client asks, server replies). WebSocket is full-duplex (server can push to client)
  - Use cases: live flight status updates, real-time chat, live pricing, live dashboard
  - Spring Boot WebSocket: `@EnableWebSocketMessageBroker`, `@MessageMapping` (receive), `SimpMessagingTemplate` (send to client)
  - STOMP protocol over WebSocket: subscribe to a topic, server broadcasts to all subscribers
- **Microservices patterns** (key ones for 24 LPA interview):
  - **Saga**: distributed transaction across services — Choreography (services react to events) vs Orchestration (central coordinator)
  - **CQRS**: separate Command (write) model from Query (read) model — scale reads and writes independently
  - **Idempotency**: same request twice = same result once — add `Idempotency-Key` header, store in Redis
  - **12-Factor App**: Config from environment (not hardcoded), stateless processes, logs to stdout
- Read: **Baeldung — `@Transactional`** + **Baeldung — Spring WebSocket** + **"12factor.net"**

### Day 26 — GenAI + RAG (Your Mondee AI Talking Point)
**Morning Theory (6 hrs)**
- **LLM basics**: Large Language Model — trained on massive text → predicts next token
  - Tokens ≈ word pieces. GPT-4 processes up to 128K tokens. Temperature = randomness.
  - You don't need to understand training — you need to understand how to use APIs
- **RAG (Retrieval-Augmented Generation)** — the 7-step pipeline you implemented at Mondee:
  1. **Document ingestion**: PDF/website → extract text content
  2. **Chunking**: split text into overlapping 500-token chunks (overlap prevents context loss at boundaries)
  3. **Embedding generation**: each chunk → OpenAI `text-embedding-ada-002` API → vector (1536 numbers)
  4. **Vector storage**: store chunk text + vector in Weaviate
  5. **User query**: user asks "Can I cancel my flight?" → generate embedding for the question
  6. **Semantic retrieval**: Weaviate finds top-5 most similar chunks (cosine similarity) → returns their text
  7. **LLM generation**: chunks + user question → OpenAI Chat API → LLM answers using only provided context
  - Why RAG over fine-tuning: no expensive retraining, data stays fresh, no hallucination on private data
- **Prompt Engineering** (what you can control):
  - System prompt: "You are a travel assistant. Answer ONLY using the provided context. If unsure, say 'I don't know'."
  - Temperature 0.0 = deterministic (good for factual Q&A), Temperature 0.7 = creative
  - Few-shot prompting: give examples in the prompt to guide format
- **NLP / Intent Detection** (Jello microservice on your resume):
  - Intent: classify what the user wants ("Cancel flight" vs "Check status" vs "Get refund")
  - Entity extraction: pull structured info from text ("Cancel my flight AK-123 on June 15")
  - Libraries: Google Dialogflow CX (enterprise), Rasa (open-source), or fine-tuned OpenAI for simple classification
- **Other APIs you used at Mondee** (be ready to explain):
  - Google Gemini: Google's multimodal LLM — similar to OpenAI but handles images too
  - DeepSeek: open-source Chinese LLM — lower cost alternative, strong at coding

## The Honest Truth
You are starting from zero. That is not a disadvantage — people who learned wrong things have to unlearn first. You start clean. Eight hours a day for 30 days = 240 hours of focused effort. That is more than most engineering graduates get in a full semester. If you follow this plan without skipping the practical blocks, by Day 30 you will have:
- Genuinely built and deployed things on AWS
- Real hands-on K8s experience
- A CI/CD pipeline that actually runs
- Monitoring setup you set up yourself
- Code on GitHub proving it

At that point the resume is not a lie. It is ahead of schedule.

### Day 1 — IAM + VPC (Foundation)
**Morning Theory (6 hrs)**
- IAM: Users, Groups, Roles, Policies (JSON), Trust Relationships
- IAM best practices: Least privilege, MFA, Role-based access
- VPC: Subnets (public/private), Route Tables, Internet Gateway, NAT Gateway
- Security Groups vs NACLs — difference and when to use which
- Watch: AWS Official — IAM & VPC deep dive (YouTube / AWS Skill Builder free)

**Evening Practical (2 hrs)**
- Log in to AWS Free Tier account (create if not done)
- Create a custom VPC with 2 public + 2 private subnets
- Create IAM roles with specific policies; attach to a user
- Test access: verify what the user can and cannot do

**Interview Questions to Prepare:**
- What is the difference between IAM Role and IAM User?
- What happens if you have conflicting Security Group and NACL rules?
- How do you secure an EC2 instance in a private subnet?

### Day 2 — EC2 + Auto Scaling + Load Balancer
**Morning Theory (6 hrs)**
- EC2: Instance types, AMIs, Key Pairs, User Data scripts
- Elastic Load Balancer: ALB vs NLB — differences, use cases
- Auto Scaling Groups: Scaling policies, Launch Templates
- EC2 Placement Groups, Spot vs On-Demand vs Reserved
- Watch: Stephane Maarek — EC2 section (Udemy AWS SA Associate course)

**Evening Practical (2 hrs)**
- Launch an EC2 instance inside your custom VPC (Day 1)
- Install Java + Spring Boot app on EC2 using User Data script
- Create an ALB and attach EC2 to a Target Group
- Set up Auto Scaling Group with min=1, max=3, desired=1
- Hit the ALB URL and verify response

**Interview Questions to Prepare:**
- What is the difference between ALB and NLB?
- How does Auto Scaling decide when to scale?
- How do you connect to an EC2 in a private subnet?

### Day 3 — S3 + CloudFront + Storage
**Morning Theory (6 hrs)**
- S3: Buckets, Objects, Versioning, Lifecycle policies
- S3 storage classes: Standard, IA, Glacier — when to use each
- S3 security: Bucket policies, ACLs, Pre-signed URLs, Block Public Access
- CloudFront: CDN basics, Origins, Cache behavior, Signed URLs
- Watch: AWS S3 deep dive — FreeCodeCamp or AWS Skill Builder

**Evening Practical (2 hrs)**
- Create an S3 bucket, upload files, enable versioning
- Write a Spring Boot endpoint that uploads a file to S3 using AWS SDK v2
- Set up a lifecycle policy: move to IA after 30 days
- Generate a pre-signed URL and test it in Postman

**Interview Questions to Prepare:**
- How do you make an S3 bucket private but allow specific users?
- What is a pre-signed URL and when do you use it?
- Difference between S3 Standard and S3-IA?

### Day 4 — RDS + Aurora + ElastiCache (Redis)
**Morning Theory (6 hrs)**
- RDS: Multi-AZ vs Read Replicas — difference, failover
- RDS vs Aurora — performance differences, Aurora Serverless
- ElastiCache: Redis vs Memcached, use cases (session, caching)
- Redis data structures: String, Hash, List, Set, Sorted Set
- Connection pooling, TTL, eviction policies
- Watch: Redis University — RU101 (free, 2-hour course)

**Evening Practical (2 hrs)**
- Spin up a Redis instance using Docker locally: `docker run -d -p 6379:6379 redis`
- Add Spring Boot Redis dependency (`spring-boot-starter-data-redis`)
- Implement response caching: cache a slow API call in Redis with 5-min TTL
- Test: first call hits DB, second call returns from Redis in <5ms
- Observe via `redis-cli MONITOR`

**Interview Questions to Prepare:**
- What is the difference between Multi-AZ and Read Replica in RDS?
- How does Redis handle expiry of keys?
- How did you use Redis in your project? (Answer: chunked file upload in Morpheus)

### Day 5 — Lambda + API Gateway + SQS/SNS
**Morning Theory (6 hrs)**
- Lambda: Event-driven, triggers, cold start problem, concurrency
- API Gateway: REST vs HTTP API, Lambda proxy integration
- SQS: Standard vs FIFO queues, visibility timeout, DLQ
- SNS: Topics, subscriptions, fan-out pattern
- Event-driven architecture patterns — when to use SQS vs SNS vs EventBridge
- Watch: TechWorld with Nana — Serverless video

**Evening Practical (2 hrs)**
- Create a Lambda function (Java or Python) triggered by an S3 upload event
- Create an SQS queue; have Lambda send a message to SQS on trigger
- Create an SNS topic; subscribe an email to it; trigger from Lambda
- Test the full flow: upload file → Lambda triggers → SQS message → SNS email

**Interview Questions to Prepare:**
- What is a cold start in Lambda? How do you reduce it?
- Difference between SQS and SNS?
- When would you use SQS FIFO vs Standard queue?

### Day 6 — ECS + EKS + CloudWatch
**Morning Theory (6 hrs)**
- ECS: Task Definitions, Services, Clusters, Fargate vs EC2 launch type
- EKS: Managed Kubernetes, Node Groups, difference from ECS
- Docker basics: Dockerfile, image layers, multi-stage builds
- CloudWatch: Metrics, Logs, Alarms, Dashboards, Log Insights queries
- CloudWatch vs Datadog — when companies use which
- Watch: TechWorld with Nana — Docker full course (first 2 hours)

**Evening Practical (2 hrs)**
- Write a Dockerfile for your Spring Boot app
- Build image: `docker build -t myapp:v1 .`
- Run locally: `docker run -p 8080:8080 myapp:v1`
- Push to ECR (Elastic Container Registry)
- Create a CloudWatch Alarm: CPU > 80% on EC2 → notify via SNS email

**Interview Questions to Prepare:**
- What is the difference between ECS Fargate and EC2 launch type?
- How do you monitor a containerized application on AWS?
- How do Docker layers work? Why does order in Dockerfile matter?
